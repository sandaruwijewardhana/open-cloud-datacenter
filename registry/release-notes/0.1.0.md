Registry v0.1.0 is the first release: a private container registry per team, in one shared Harbor. It has two parts:

- **Operator**: runs on the Harvester cluster as an Addon. A `Registry` in any namespace becomes a Harbor project, a storage quota and two credentials. The API is `registry.opencloud.wso2.com/v1alpha1` and may change in later releases.
- **Rancher UI extension**: create, view, resize and delete registries from Rancher, with ready-to-copy commands to push and pull.

The operator does not deploy Harbor. You run Harbor; the operator manages projects inside it.

## What a registry gives you

- A private Harbor project named `<name>-<8 hex of the Registry's UID>`, with the plan's storage quota: `starter` 5 GiB (default), `professional` 20 GiB, `enterprise` 100 GiB. The plan can be changed later.
- Two `kubernetes.io/dockerconfigjson` Secrets beside it: `<name>-pull` (pull only) and `<name>-push` (pull, push, tag, delete, for build pipelines). Usable directly in `imagePullSecrets` and by `docker login`.
- Users with the built-in `edit` role in a namespace manage registries there; `view` can read them.
- Deleting a credential Secret revokes it in Harbor and issues a new one. Deleting a `Registry` deletes its Harbor project and images.
- Uninstalling the operator keeps the CRD, every `Registry` and every Harbor project.

## Requirements

- Harvester 1.9.0 (the tested version).
- Harbor 2.15 (tested with 2.15.2, chart 1.19.2), reachable over HTTPS at one fixed hostname, and a Harbor system-administrator account for the operator.
- A route from Harvester pods to Harbor, or reserved addresses on Harbor's VLAN for a Multus attachment.
- Every node and machine that pulls must trust Harbor's certificate. A private CA is not distributed by the operator.
- For the UI extension: Rancher 2.15 or later (tested on 2.15.2).

## Install

1. On the Harvester cluster, create the namespace: `kubectl create namespace registry-system`.
2. In the attached `registry-operator-addon.yaml`, fill in Harbor's URL, the operator's Harbor login and Harbor's CA certificate (or remove the CA for a publicly-rooted certificate), then apply it: `kubectl apply -f registry-operator-addon.yaml`. Check it with `kubectl get addon registry-operator -n registry-system`.
3. In Rancher, as an admin: **Extensions** → ⋮ → **Manage Extension Catalogs** → **Import Extension Catalog**, using the UI extension image listed under Artifacts. Then install **Registries** from the **Available** tab.

For the network attachment, upgrades and uninstalling, see `registry/INSTALL.md`. For the UI, see `registry-ui/docs/USER-GUIDE.md`.

## Changes from pre-release builds

- `.status.credentialsSecretName` is replaced by `.status.pullSecretName` and `.status.pushSecretName`, and the single Opaque credentials Secret by the two `dockerconfigjson` Secrets.
- `RegistryBackend` no longer exists, and the operator no longer deploys Harbor.
- `HARBOR_URL` must be https; plain http needs `harbor.allowPlaintextURL: true`.

## Known limitations

- The operator authenticates to Harbor as a system administrator (#300). Keep its credentials Secret readable only by cluster administrators.
- Credentials do not expire. Revoke one by deleting its Secret; every copy on other clusters stops working at once.
- Changing Harbor's URL does not rewrite existing credential Secrets. Treat the Harbor hostname as permanent.
